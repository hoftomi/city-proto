# Trón nélkül – 0.0.2

An asynchronous strategy game built around the city's three branches of power: Merchants (Marketplace, *Vásártér*), Politics (Town Hall, *Városháza*), Spy Network (Underworld, *Alvilág*). This version contains a complete thin slice: social sign-in, game browser and joining, and the game itself (map, city view, order sheet, reports, ranking). The rules engine runs on the server according to **rulebook v0.2**: a sealed order sheet executes after its maturation time, and the economy settles at 8:00 and 20:00.

| Part | Technology |
|---|---|
| `backend/` | Spring Boot 4.1.1, Java 25, Spring Security 7 (Firebase ID token), Spring Data JPA, Flyway, PostgreSQL 17 |
| `mobile/` | Flutter 3.47 (Dart 3.13), Android and iOS, Firebase Auth |
| `docker-compose.yml` | PostgreSQL, optionally together with the backend |

> The 0.0.2 backend compiles, the rules engine tests pass (`./gradlew test`), and the mobile `flutter analyze` is clean. The mobile models can parse the state JSON produced by the backend. The full flow has not yet been tried end to end on a real device with a signed-in user.

## 1. Quick start

### Prerequisites

- JDK 25. The Gradle toolchain downloads it automatically if it is not installed.
- Docker (for PostgreSQL).
- Flutter 3.47 stable (`flutter --version`), plus Android Studio or Xcode.
- A Firebase project, the `firebase` CLI and the `flutterfire` CLI (`dart pub global activate flutterfire_cli`).

### Backend

```bash
docker compose up -d db          # PostgreSQL on port 5432 (tron / tron / tron)
cd backend
./gradlew test                   # rules engine tests
./gradlew bootRun                # http://localhost:8080 (Firebase project: city-proto)
```

On first start, `SeedData` creates the sample games:

| Game | Status | Note |
|---|---|---|
| Délkelet · 1. szezon (Southeast · Season 1) | **running** | Joining is possible until the first 3 settlements, so it can be tried right away. |
| Ködös Hegyvidék (Misty Highlands) | open | starts in +2 days |
| Sóvidék ligája (Saltland League) | open | starts in +5 days |
| Villámszezon (Lightning Season) | open | starts in +1 day |
| Tavaszi bajnokság (Spring Championship) | announced | registration opens in +12 days |

Check: `curl localhost:8080/actuator/health`.

### Mobile

The repo does not contain the platform folders (`android/`, `ios/`), because they are generated by the installed Flutter version. Run the setup script once:

```bash
cd mobile
./setup_platforms.sh        # flutter create + Android settings + flutter pub get
flutterfire configure       # select the Firebase project: firebase_options.dart, google-services.json, GoogleService-Info.plist
flutter test
flutter run
```

The script does the following:

- runs `flutter create . --org com.hof --project-name tron_nelkul --platforms android,ios` (`--project-name` is needed because the folder name is not necessarily a valid Dart package name; the existing `lib/` and `pubspec.yaml` are not overwritten);
- copies in `platform/android/AndroidManifest.xml`: internet permission, development HTTP (`usesCleartextTraffic`), the Discord sign-in callback activity;
- sets the Android `minSdk` to 24 (required by `flutter_secure_storage`).

**On the Android emulator** the backend address defaults to `http://10.0.2.2:8080`; **on a real phone** use your machine's local IP address: `--dart-define=API_BASE=http://192.168.x.y:8080`.
**On the iOS simulator** the backend address is `http://localhost:8080`. For another address: `--dart-define=API_BASE=https://…`.

### Trying it out

1. Sign in with a Google account (see chapter 2 for the setup). Every new user gets the PLAYER role. The ADMIN role (for time skipping and immediate settlement) can be granted in the database:
   `update users set role = 'ADMIN' where display_name = '<your name>';` It takes effect on the next request; no need to sign in again.
2. In the game browser open the **Délkelet** game and choose the „Csatlakozás a futó játékhoz” (Join the running game) button. Then come the four steps: house, background (Merchant House: pick a good in the starting city), starting position, summary.
3. Open the game:
   - **Map:** tap a city: your popularity, goods, council. If none of your routes lead there, you can build one from here.
   - **City:** three districts. **Marketplace:** buying shares from the City, margin, buyout and defensive purchase. **Town Hall:** founding a party, tax program, festival, news. **Underworld:** spies, guards, scouting, verifying and debunking news, selling information.
   - **Order sheet:** you seal the draft, and it takes effect after 2 hours of maturation (1 hour in Lightning Season). You can have only one maturing sheet at a time.
   - **Reports** (your own and public) and **Ranking** (Legitimacy, shares, council seats).
4. As an admin you can skip time in the top bar (+30 minutes, +2 hours, next event), or settle immediately. Skipping ahead moves the game's own clock (`games.time_offset_minutes`), not real time.

In production, settlement runs every day at 8:00 and 20:00 (Europe/Budapest), and every 6th settlement is an election. The scheduler executes expired order sheets every half minute.

## 2. Sign-in (Firebase Auth)

Sign-in is handled by Firebase Authentication. The mobile app sends its Firebase ID token with every request (`Authorization: Bearer`). The backend verifies the signature with Google's keys, as well as the issuer (`https://securetoken.google.com/<project-id>`) and the audience. On the first request it creates its own user (`users`, `user_identities` with `provider = firebase`, `subject` = Firebase uid). There is no password and no developer login.

The environment variables are listed in `.env.example`. Copy it as `.env`.

### Firebase project

1. Create a project in the Firebase Console, and run `flutterfire configure` in the mobile folder (Android: `com.hof.tron_nelkul`, iOS: `com.hof.tronNelkul`). This overwrites the `lib/firebase_options.dart` placeholder and puts the platform configuration files in place.
2. Backend: `FIREBASE_PROJECT_ID` (default: `city-proto`).

### Google

1. Firebase Console → Authentication → Sign-in method → enable **Google**.
2. Android: in the Firebase project settings, add the SHA-1 and SHA-256 fingerprints of the signing key (`cd android && ./gradlew signingReport`), then run `flutterfire configure` again.
3. iOS: add the `REVERSED_CLIENT_ID` value from `GoogleService-Info.plist` as a URL scheme in `ios/Runner/Info.plist` (as described in the `google_sign_in` docs).
4. If sign-in on Android fails with a "serverClientId" error: `--dart-define=GOOGLE_SERVER_CLIENT_ID=<the "Web client" id created by Firebase>`.

### Apple (iOS only)

1. Firebase Console → Authentication → Sign-in method → enable **Apple**.
2. In the Apple Developer portal enable the *Sign in with Apple* capability for the bundle ID, and in Xcode add a "Sign in with Apple" capability to the Runner target.
3. Apple only passes the name on the first sign-in. The client then writes it into the Firebase account, so the backend reads it from the ID token.

> If the iOS app offers other social sign-ins, App Store rules make Sign in with Apple mandatory.

### Discord

Firebase does not support it natively. The mobile app requests a code in the system browser with the authorization code + PKCE flow (`flutter_web_auth_2`). The backend redeems it, fetches the Discord profile and returns a Firebase custom token (uid: `discord:<Discord id>`). The client uses it to sign in to Firebase.

1. Create an application in the Discord Developer Portal. Under OAuth2, add the redirect URI: `tronnelkul://auth`.
2. Backend: `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`, and a Firebase service account key for signing custom tokens. Download it from Firebase Console → Project settings → Service accounts → "Generate new private key". Put it at `backend/secrets/firebase-service-account.json` (ignored by git), and set the `GOOGLE_APPLICATION_CREDENTIALS` variable to the file's path. In Docker it can be mounted with the commented-out lines of `docker-compose.yml`.
3. Mobile: `--dart-define=DISCORD_CLIENT_ID=<ID>`. On Android the callback activity is already in `AndroidManifest.xml`.
4. If Discord does not accept the custom scheme, use an https redirect page and pass `--dart-define=DISCORD_REDIRECT_URI=…` and `DISCORD_CALLBACK_SCHEME=…`.

### Before going live

- Replace the sign-in buttons with the providers' official buttons that follow their brand guidelines. For now the game intentionally uses neutral letter marks.
- HTTPS in front of the backend.
- With multiple server instances the scheduler must run on only one instance: set `SCHEDULER_ENABLED=false` on the others.

## 3. Structure

```
backend/src/main/java/com/hof/tronnelkul/
  auth/            Firebase ID token → own user, Discord PKCE → Firebase custom token
  config/          security (stateless, Bearer Firebase ID token), settings
  user/            users and their external identities
  game/world/      maps (Délkelet, Ködös Hegyvidék, Sóvidék): cities with goods, roads, starting positions, terrain
  game/engine/     the rules engine: plain Java, no Spring, with unit tests
                   Rules (chapter 11 of rulebook v0.2), EngineState (the state), Engine (maturation, settlement,
                   election, spies, news, information market, NPCs), Setup (initial position, background bonus)
  game/model/      JPA entities; the game state is a JSON document in the games.state column
  game/service/    lobby, joining, orders, view, scheduler, seed data (GameRunner: locking, advancing, saving)
  game/api/        REST controllers (implementations of the generated API interfaces)
backend/src/main/resources/db/migration/   the schema (V2: v0.2, deletes the old games)

mobile/lib/
  api/             HTTP client, models (mirror of Dtos.java), session
  auth/            Google, Apple, Discord (Firebase Auth)
  theme/           design system tokens (colors in light and dark theme, fonts, spacing)
  widgets/         design system components: share bar, council seats, PP counter, crest, report card,
                   map (with terrain), city view (Town Hall, Marketplace, Underworld)
  screens/         sign-in, game browser, details, joining, game (5 tabs; city_tab.dart: the three districts)
```

The rules engine runs on the server. Public information: the sellers' names, shares and tier (5.2), popularity, parties, the council and the news. You can only see other players' order sheets by scouting, and you cannot see how many spies others have, only that they have some.

## 4. API

The contract is at the repo root: [`api/openapi.yaml`](../api/openapi.yaml). On every build the backend generates the interfaces (`com.hof.tronnelkul.api`) and models (`com.hof.tronnelkul.api.model`, openapi-generator `spring`) from it. The controllers implement them, and the mobile client generates from the same file. Details: [`api/README.md`](../api/README.md).


| Method | Path | Description |
|---|---|---|
| POST | `/api/auth/discord` | Discord code exchange, response: `{customToken}` (Google and Apple go directly through Firebase) |
| GET | `/api/me` | the signed-in user (created by the first call) |
| GET | `/api/games/joined` | the user's live games (running, open, announced), with the own house |
| GET | `/api/games/available` | live games the user has not joined |
| GET | `/api/games/archived` | finished games the user played in, newest first, with the winner and the own place |
| GET | `/api/games/{id}` | details, starting positions, backgrounds, tinctures |
| GET | `/api/games/maps/{mapId}` | map (cities, roads, starting positions, terrain) |
| POST / DELETE | `/api/games/{id}/join` | joining and withdrawal |
| GET | `/api/games/{id}/state` | the player's view: clock, resources, network, cities, draft, maturing sheet, threats, scouted plans, offers, catalog |
| POST | `/api/games/{id}/orders` | order on the draft (`type`: route, margin, buyShares, buyout, defend, foundParty, program, festival, news, hireSpy, moveSpy, guard, spy, verify, debunk) |
| DELETE | `/api/games/{id}/orders/{orderId}` | delete an order from the draft |
| POST | `/api/games/{id}/seal` | sealing (cannot be undone) |
| POST | `/api/games/{id}/intel/{intelId}/offer` | offer a scouted plan for sale: `{buyerId, price}` |
| POST | `/api/games/{id}/offers/{offerId}/accept` · `/decline` | accept (escrow) or decline an offer |
| GET | `/api/games/{id}/reports` · `/ranking` | reports, ranking |
| POST | `/api/admin/games/{id}/start` · `/settle` · `/advance` | start, immediate settlement, time skip by `{minutes}` or to the next event (ADMIN) |

Every error comes as an RFC 9457 ProblemDetail. The `detail` field is displayable Hungarian text.

## 5. Limitations and deviations of 0.0.2

- **Base price:** 3 gold per unit, as in the prototype. The rulebook suggests 1 gold, but that makes the economy too tight.
- **Defensive purchase:** it takes effect if you seal it before the buyout executes. It does not have to execute first; otherwise, with equal maturation times, the target could never defend itself.
- **Scouting:** reveals only the orders issued in the given city (7.2; the prototype shows the whole sheet). Every spy action can be exposed, including verifying and debunking news (7.4).
- **NPCs:** play with the same maturation time as the players, and can seal at any time (within 6 hours after a settlement, or after their sheet has executed).
- **Still missing:** difficulty levels and modules (9.), and push notifications. The NPCs' network is unrestricted (they have no estates and no routes), and they do not yet react to spy reports.
- **Tincture:** not unique, because 8 colors are not enough for 30 players. House names are unique.
- **Needs testing:** a passive Shadow Order player runs out of gold in 3 days (maintaining 2 spies and 2 routes costs 6 gold per settlement). The espionage branch needs income early, otherwise this is the rulebook's question 12.3.
